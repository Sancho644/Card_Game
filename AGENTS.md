# Card_Game

Используй правила разработки из `CLAUDE.md` и Git-процесс из этого раздела.

## Git Workflow and Single Working Copy

### Рабочая папка

- Единственная рабочая копия проекта — `D:\Unity\Projects\Card_Game`. Все изменения проекта и переключения веток выполняй в этой папке.
- Для новых задач запрещено создавать worktree, в том числе через автоматизацию, копировать Unity-проект или клонировать репозиторий.
- Для управления ветками предпочитай Git CLI в PowerShell или терминале. Fork использует сам пользователь. Не запускай Fork автоматически и не делай его обязательным.

Перед каждой задачей выполни в основной папке:

```powershell
git rev-parse --show-toplevel
git branch --show-current
git status --short --branch
git worktree list
```

Убедись, что корень Git соответствует `D:\Unity\Projects\Card_Game`. Перед любым переключением повторно проверь статус и список worktree. При ошибке проверки останови переключение и сообщи пользователю причину.

### Начало и продолжение задач

- Для самостоятельной задачи создай одну feature-ветку от актуального `origin/main`. Для продолжения работы используй существующую ветку.
- При любых незакоммиченных изменениях, включая staged и untracked, останови переключение и сообщи пользователю о состоянии рабочей папки. Не удаляй и не перезаписывай изменения. Не используй `git reset --hard` или `git clean`. Не делай `git stash` без согласования.
- Если целевая ветка занята другим worktree, останови переключение. Сообщи имя ветки, путь и способ безопасно её освободить. Сначала проверь статус в занятом worktree. Сохранение изменений и освобождение ветки согласуй с пользователем. Удалять старый worktree можно только после проверки его чистоты и с явного разрешения пользователя. Не обходи ограничения Git на занятые ветки.

Для новой feature-ветки после проверок:

```powershell
git fetch origin
git status --short
git switch main
git pull --ff-only origin main
git switch -c feature/<task-name>
```

До создания ветки проверь, что `main` совпадает с `origin/main`. Если fast-forward не удался или вершины различаются, остановись и сообщи об этом.

Для продолжения существующей feature-ветки после проверок:

```powershell
git fetch origin
git switch feature/<task-name>
git pull --ff-only origin feature/<task-name>
```

Выполняй pull для feature-ветки, если соответствующая ветка уже есть в `origin`. При ошибке fast-forward сообщи о расхождении.

### Завершение feature-задачи

1. Выполни необходимые тесты и проверь сборку.
2. Проверь `git status` и создай коммит с изменениями задачи.
3. Опубликуй ветку командой `git push -u origin feature/<task-name>`.
4. Подготовь Pull Request в `main` и дождись успешных CI-проверок.

После успешной публикации и сохранения всех изменений можно вернуться на `main` командами `git switch main` и `git pull --ff-only origin main`. Перед переключением снова проверь статус и worktree. Если пользователю нужно проверить feature в Unity, оставь её активной до его решения. Приоритет имеют ограничения пользователя для конкретной задачи.

### Unity при смене ветки

- Сохраняй `Library` и локальные сборки. Не удаляй `Temp` без обоснованной причины, а `Logs` — без разрешения пользователя.
- Сохраняй версию Unity Editor и GUID существующих ресурсов. Меняй GUID только при необходимости для задачи. Не пересоздавай проект и не копируй вручную `Packages` и `ProjectSettings`.
- После переключения дождись обновления AssetDatabase. Если Unity уже открыта, учти автоматический импорт и перезагрузи проект при необходимости. Для основной рабочей копии используй один экземпляр Unity Editor.
